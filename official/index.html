How it connects

There is no cloud in between and nothing new to expose. The app uses the SSH you already run. For your team, the server dials out.

The agent only listens on a unix socket. It never binds a port. Only root, or a group you name, can reach it.

Admins come in over SSH. Every request is one short srvmon-agent api command on the connection you already have.

Team members never get SSH. The agent connects out to the relay, and checks every member request itself.

  1. Add a server

    Enter the host and the user. The app connects over SSH, uploads the agent, checks its SHA-256, installs it as a systemd service and waits until it answers. There is nothing to install by hand.

  2. Watch it

    Open a server and the app asks the agent every five seconds over the same connection. The agent reads /proc, the Docker socket, systemd and the journal and keeps an hour of history.

  3. Invite your team

    Members join with a QR code, not with SSH access. Their phones reach the servers through the relay, and the agent checks the signature and the scope of every request before it answers.

A health check you can run, and alerts you don't have to

Health check runs a fresh set of checks on demand: connection time, CPU, load, memory, swap, every disk, inodes, Docker, problem containers, failed services, OOM kills in the last day, clock drift, a pending reboot and whether the other servers are reachable. Each line is green, amber or red, with a hint when it isn't green.

Alerts are evaluated on the server by the agent, so they work while the app is closed. The defaults: CPU above 90% for five minutes, memory above 85% for two, disk above 85%, a container that exits with an error or is killed for memory, an unhealthy container, a restart loop, a failed systemd unit, a peer that stops answering. The same alert repeats at most every fifteen minutes and tells you when it is resolved.

Disk space back, without guessing

Disk analysis breaks the disk down into Docker images, build cache, volumes, container logs and layers, each with its reclaimable amount, then lists folders by size and the largest files. Tap into a folder to see what is inside.

Smart cleanup separates what is safe from what you should look at first. Build cache, dangling images, oversized container logs, package caches, old journal entries, rotated logs and language package caches are safe. Unused images and node_modules or vendor folders wait for your tick. Anything a running container mounts or a process works in is locked and stays. Volumes are never touched.

  • Metrics with history

    CPU, memory, disk and load, refreshed every five seconds, with the last hour as a chart. Problem servers sort to the top of the list.

  • systemd services and the journal

    Every unit on the server, failed ones first, each with its journal. The Docker engine's own journal sits at the top of the containers list.

  • File manager

    Browse, view and edit files with line numbers and search. Every save makes a backup and writes atomically. Upload from the Files app over SFTP. System paths stay read-only.

  • Terminal

    A real SSH terminal with 256 colors. htop, vim and journalctl -f work as they should, with shortcut keys for the commands you type most.

  • Push alerts

    Notifications come straight from your server through Apple's push service with your own key. No appinsource server is involved.

  • Servers watch each other

    Each agent can ping the others, so you hear about a server that went down from the ones still up.

Built so that the app can't be the weak point

A monitoring app holds the keys to your servers. These are the rules it keeps.

  • No port is opened.

    The agent listens on /run/srvmon/agent.sock, readable by root or by a group you name. The relay connection, if you use one, is made by the server and goes outbound.

  • Passwords are not stored.

    If a server only accepts a password, the app uses it once to install its own key, then forgets it. Keys live in the iPhone Keychain and are never exported.

  • Host keys are pinned.

    The first connection records the server's host key. If it changes later, the app refuses to connect and tells you why.

  • Team requests are signed.

    Each member's phone signs every request with its own Ed25519 key. The agent checks the signature against the member list that the admin pushed over SSH, applies the member's scope, and rejects replays. A compromised relay can't make an agent do anything a member isn't allowed to do.

  • Logs and services are for admins only.

    Logs can contain secrets and customer data, so Viewers and Operators never receive them. Containers outside a member's scope are filtered on the server and never leave it.

  • Files are for the SSH admin only.

    File requests through the relay get a 403. System paths and the agent's own files are read-only, every save keeps a backup, and writes are atomic.

  • The app locks with Face ID.

    On by default. You can switch it off in Settings.

Monitoring without handing over root

Some servers keep root login locked behind two-factor codes or a maintenance window, and some admins would rather not give an app root at all. For those, monitoring goes through a user that can do one thing.

The server's admin creates a srvmon user once. It can log in only with the iPhone's key, has no password, no sudo, is not in the docker group and cannot forward ports. The app logs in as srvmon and talks to the same agent, which runs as a service the admin installed. Root login stays exactly as it was.

The app generates everything the admin needs: the agent binary for the server's architecture and a setup script with this iPhone's key already in it. Running the script again later updates the agent and keeps the user, the keys and the config.

Read the guide for server admins

  1. Generate the script

    In the app: Servers, add, User srvmon, then Server setup script. Share the binary and copy the script.

  2. Copy the binary to the server

    With the scp command the app shows, to /tmp/srvmon-agent.

  3. Run the script as root

    It creates the user, adds the key, installs the agent and tests itself. The last line is OK.

  4. Connect

    Back in the app, tap Connect to existing agent. The app installs nothing and saves the server.

Scopes

A scope is a pattern over container name, image or compose project. Set it per member and per server.

  • erp-*erp-backend, erp-db, erp-frontend, and whatever you add later
  • n8nOnly the container, image or project named exactly n8n
  • *db*Everything with db in its name
  • *Every container on that server
  • emptyNo containers. Server health only.

The relay

A single Go binary, or a container, that you run behind your own reverse proxy. Agents long-poll it outbound; members' phones call it over HTTPS. It routes requests and stores names and hashed tokens, nothing more.

Questions

Does it open any port on my servers?

No. The agent listens on a unix socket. The app comes in through SSH, which you already run. For team access the server connects out to the relay over HTTPS; nothing connects in.

Does the agent send data anywhere?

Only to your phone over your SSH session, and to the relay if you set one up. There is no appinsource backend, and this site has no analytics.

What if I lose my phone?

Remove its key from each server. On the server, one line does it: sed -i '/server-monitor-ios/d' ~/.ssh/authorized_keys. For a srvmon user, edit that user's authorized_keys instead. Team members are revoked from the app and lose access at once.

Do I need Docker?

No. The Docker card and the containers list simply stay empty. Everything else works.

Can team members read logs?

Only Admins. Viewers see server health and the containers in their scope. Operators can also start, stop and restart those containers.

Can I run the relay myself?

That is the only way it runs. It is a single Go binary or a Docker container behind your own reverse proxy, with a token you keep.

How do I get the app?

It is not on the App Store yet. Write to us and we will set it up with you on your iPhone.
