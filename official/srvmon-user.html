Monitoring through a srvmon user

Server Monitor watches your servers from an iPhone. It does not have to log in as root. On a server where root login is locked, or where you would rather not hand root to an app, monitoring goes through a user that exists for this one job: srvmon. This page is for the server's admin and explains how to set it up.

How it works

  • A small program, srvmon-agent, runs on the server. It reads CPU, memory, disk, Docker containers, services and logs.
  • The agent opens no port. It listens only on a local socket inside the server.
  • The iPhone connects over SSH as srvmon and asks the agent its questions through that socket.
  • srvmon cannot log in with a password, only with the SSH key the phone generated. The phone's private key never leaves the phone.
  • srvmon has no sudo, is not in the docker group and cannot forward ports. The only thing it can do is talk to the agent.
  • Whatever your root login looks like, it stays that way. This setup does not touch root's settings.

What you need

  • Root on the server, once, from a terminal, a hosting panel or through an admin.
  • systemd on the server: Ubuntu, Debian or the RHEL family. Alpine is not supported.
  • Two things the app generates for you. In the app: Servers, add, type srvmon in User, tap Server setup script.
    1. The agent binary (srvmon-agent-linux-amd64 or arm64). Share binary sends it to a Mac by AirDrop or saves it to Files.
    2. The setup script, with this phone's SSH key already written into it. Copy script or Share script.

Steps

  1. Copy the agent binary to the server. Use the scp command the app shows. The file must land at /tmp/srvmon-agent: 
    scp srvmon-agent-linux-amd64 root@SERVER:/tmp/srvmon-agent
  2. Run the script on the server as root. Paste it into a file and run sh srvmon-setup.sh, or paste its contents straight into a root shell.
  3. Check the last line. The script tests itself and ends with OK. An HTTP 200 line shows that the agent answers the srvmon user.
  4. Connect in the app. On the add-server screen: User srvmon, login method iPhone key, then Connect to existing agent. The app installs nothing. It checks that the agent answers and saves the server.

What the script does, exactly

  1. Creates the srvmon group and user. The password is locked; the home directory is /home/srvmon.
  2. Adds the phone's public key to /home/srvmon/.ssh/authorized_keys. The same key is never added twice.
  3. Writes /etc/ssh/sshd_config.d/40-srvmon.conf: for srvmon, password and interactive login are off, and TCP, agent and X11 forwarding are off. It validates the config with sshd -t and reloads sshd. Other users' settings are untouched.
  4. Verifies the SHA-256 of the agent binary and installs it as /usr/local/bin/srvmon-agent.
  5. Creates /etc/srvmon/config.json if it does not exist: server name, socket path, "socket_group": "srvmon" and "allow_actions": true (start, stop and restart of containers from the app). An existing file is left as it is.
  6. Writes the srvmon-agent systemd service, enables it at boot and starts it. The service runs as root (it needs the Docker socket and the journal) and opens its socket /run/srvmon/agent.sock as root:srvmon 0660.
  7. Tests itself: agent version, a health query as srvmon, the socket's permissions, the user's groups.

Running the script again is safe: the user, the keys and the config are kept. This is also how the agent is updated: copy the new binary to /tmp/srvmon-agent and run the script again. When a server's agent is older than the app's, the app shows a yellow strip on that server's card.

More than one iPhone

Each phone has its own key. On the second phone, follow the same path: get the script from that phone's app and run it on the server. It adds that phone's key and keeps the earlier ones.

Security notes

srvmon gets no root rights in a shell. But the agent runs as root, so through the app every feature of the agent is available: starting and stopping containers, reading logs, and reading, editing, deleting and uploading files with the file manager (system paths and /etc/srvmon are protected). Whoever holds the phone's key holds that power. If you lose the phone, delete its key from /home/srvmon/.ssh/authorized_keys.

  • If you do not want container actions, set "allow_actions": false in /etc/srvmon/config.json and run systemctl restart srvmon-agent.
  • The setup opens no port, does not touch the firewall and does not change root login.

Removing it

systemctl disable --now srvmon-agent
rm -f /etc/systemd/system/srvmon-agent.service /usr/local/bin/srvmon-agent
rm -rf /etc/srvmon /var/lib/srvmon /etc/ssh/sshd_config.d/40-srvmon.conf
systemctl daemon-reload && sshd -t && systemctl reload ssh
userdel -r srvmon; groupdel srvmon 2>/dev/null
